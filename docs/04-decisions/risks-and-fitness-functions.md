# Архитектурные риски, risk storming и функции пригодности

*Источник: главы 6 и 22; сквозные связи — глава 26. Риск-реестр и типы контроля ниже — авторские инструменты.*

## Что такое архитектурный риск

Риск — не просто «нам не нравится система». Формулируйте его как **возможное событие + нарушаемое свойство + последствия + условие наблюдения**.

Плохая запись: «очередь может сломаться».
Хорошая: «при 20-минутной недоступности брокера сервис начинает подтверждать заказ, но не сохраняет событие об оплате; возможно рассогласование прав пользователя и поступивших денег».

## Карта рисков

| Класс | Пример | Признак в эксплуатации |
|---|---|---|
| Эксплуатационный | БД на критическом пути без отказного режима | Рост ошибок при отказе БД |
| Структурный | Циклическая зависимость модулей | Невозможно релизить изменения локально |
| Данные | Неидемпотентная оплата | Повторное применение одного платежа |
| Безопасность | Неавторизованный межсервисный вызов | Отсутствие проверки service identity |
| Организационный | Нет владельца сервисов | Инциденты остаются без реакции |
| Эволюционный | Все изменения требуют миграции общей схемы | Cross-team release coordination |

## Risk storming — практический процесс

В главе 22 обсуждаются выявление рисков, согласование оценки и меры снижения. Прикладной формат сессии:

1. Нарисуйте **текстовую** карту компонентов и потоков.
2. Назовите критические сценарии качества.
3. Индивидуально предложите отказные сценарии, не споря о решениях.
4. Согласуйте место риска, вероятность и тяжесть последствий.
5. Выберите немедленные проверки для наиболее существенных рисков.
6. Назначьте владельцев и сроки, не оставляйте безымянных красных зон.

Можно применять матрицу **вероятность × влияние**, но это приближённый инструмент. Не создавайте впечатление, что числа 1–5 предсказывают точную вероятность в процентах.

## Что делать с риском

- **Избежать:** изменить структуру и убрать риск.
- **Уменьшить:** изоляция, тесты отказов, backups.
- **Передать:** перенести часть ответственности по договору, не снимая свою.
- **Принять:** явно решить, что стоимость меры выше ожидаемого ущерба; задокументировать.

## Fitness functions

**Функция пригодности** — механизм объективной оценки того, соответствует ли архитектура нужному свойству. Может выполняться постоянно, при сборке, по расписанию или в ходе эксплуатационного эксперимента.

| Заявление | Проверка | Реакция |
|---|---|---|
| Billing не зависит от UI | Запрет импортов в CI | Блокировать merge |
| Оплата идемпотентна | Нагрузочный тест параллельных повторов | Исправить переход состояния |
| Резервные копии пригодны | Тест восстановления с измерением RPO/RTO | Эскалация владельцу данных |
| Критический API в SLO | Мониторинг p95 и error rate | Анализ инцидента / rollback |
| Сервис можно выпускать независимо | Проверка совместимости контрактов | Отложить несовместимый релиз |

**Отдельно:** guardrail без наблюдаемости быстро превращается в устаревшее правило. При изменении контекста обновляйте и саму проверку, и ADR.

## Пример минимального риск-реестра

~~~text
Risk ID: R-004
Сценарий: повторная доставка PaymentConfirmed
Эффект: двойное продление подписки
Вероятность: требует оценки по фактам
Тяжесть: высокая
Проверка: конкурентный тест + уникальный бизнес-ключ
Владелец: team billing/subscriptions
Статус: проверка не реализована
~~~

Не записывайте «исправлено», пока не увидели успешную проверку на ожидаемом отказном сценарии.

## Ревью перед выпуском

1. Назначены ли владельцы критических качеств?
2. Выполняются ли восстановление и резервное копирование на практике?
3. Нет ли единой точки отказа в критическом пути?
4. Есть ли автоматический контроль структурных границ?
5. Существуют ли runbook, алерты и пороги для важных рисков?
6. Пересматриваются ли ADR после инцидентов?
