# Транзакции в распределённых системах, saga и повторные доставки

*Темы книги: главы 15, 18 и 20 (особенно транзакции и саги, стр. 376+). Outbox/inbox и подробные процедуры отказов — наши прикладные дополнения.*

## Почему локальной транзакции не хватает

В одной БД транзакция может атомарно обновить связанные таблицы. Но операция «изменить Subscription, запросить внешний платёж, отправить email» пересекает независимые системы. Обычная транзакция базы не откатывает внешний API и уже доставленное письмо.

**Требование архитектора:** выбрать границу атомарности и отдельно определить, как согласовываются результаты вне этой границы.

## Пример: оформление платного доступа

~~~text
Create order (локально)
      ↓
Initiate payment (внешняя система)
      ↓
Receive confirmation (может прийти повторно)
      ↓
Activate subscription (локально)
      ↓
Send notification (может опоздать)
~~~

Если пользователь получил квитанцию, а подписка не активировалась, это **не просто техническая ошибка очереди**: нужен бизнес-процесс исправления и сверки.

## Saga: последовательность локальных шагов

**Saga** — модель долгой бизнес-операции, где каждый шаг совершает свою локальную транзакцию, а неудача может запускать **компенсирующее действие**. Компенсация не обязательно возвращает мир в идентичное предыдущее состояние: отмена брони и возврат денег сами по себе имеют бизнес-смысл и могут не удаваться.

| Шаг | Действие | Возможная компенсация |
|---|---|---|
| ReserveCapacity | Резервировать место | ReleaseCapacity |
| AuthorizePayment | Авторизовать сумму | VoidAuthorization |
| ConfirmOrder | Подтвердить заказ | CancelOrder по политике |
| NotifyCustomer | Отправить сообщение | Не имеет обратного физического действия |

**Orchestration** даёт один координатор шагов; **choreography** распределяет реакции между участниками. Выбор зависит от сложности ветвлений и нужного контроля над процессом.

## Идемпотентность

При at-least-once доставке обработчик может получить событие несколько раз. Уникальный ключ операции позволяет определить, обработана ли она ранее. Важно идемпотентно выполнять **бизнес-эффект**, а не просто возвращать HTTP 200.

~~~text
begin transaction
  if event_id already processed:
      return previously recorded outcome
  apply business state transition with invariant checks
  remember event_id as processed
commit
~~~

Детали зависят от СУБД и конкуренции транзакций; уникальный индекс и корректная атомарная запись предпочтительнее «проверил, потом записал» без защиты от гонки.

## Transactional outbox

Проблема dual write: сначала записали изменение в БД, затем попытались отправить событие. Между действиями процесс может умереть. **Outbox** помещает изменение бизнес-состояния и запись будущего события в **одну локальную транзакцию**. Отдельный relay публикует событие повторно до подтверждения. Потребитель всё равно должен ожидать дубликаты.

~~~text
Local DB transaction:
  update subscription
  insert outbox(event_id, payload, status=new)
COMMIT

Relay:
  read unsent events → broker → mark published (may retry)

Consumer:
  dedupe by event_id → apply effect → acknowledge
~~~

**Outbox не даёт магического exactly-once для внешнего мира.** Зато закрывает конкретное окно потери между БД и публикацией.

## Что делать с ошибками

- **Transient failure:** ограниченные повторы с backoff и jitter.
- **Permanent failure:** DLQ или ручной разбор с контекстом.
- **Poison message:** изолировать проблемное сообщение, не останавливая обработку всех.
- **Partial completion:** хранить состояние workflow и причину остановки.
- **Lost callback:** проводить сверку с внешним источником истины, если бизнес допускает такое расхождение.
- **Duplicate action:** проверять уникальный бизнес-ключ, а не только ID сетевого запроса.
- **Unexpected reorder:** применять версии агрегата, условные обновления или маршрутизацию с порядком по ключу.

## Инварианты важнее красивой последовательности

Задайте для состояния подписки допустимые переходы. Например, «подписка не получает новый срок действия дважды по одному payment reference». Тестируйте конкурентные вызовы, длительные задержки и переупорядоченные события.

## Проверка перед production

1. Есть сценарий повторной доставки и конкурирующей обработки.
2. Можно восстановить процесс после аварии любого участника.
3. Записи журнала позволят объяснить итог клиенту и оператору.
4. Retry не создаёт неконтролируемого платежного или ресурсного эффекта.
5. SLA внешней зависимости и длительность незавершённой саги известны.
6. Есть наблюдаемый механизм ручного исправления и сверки.
