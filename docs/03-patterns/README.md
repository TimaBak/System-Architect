# III. Архитектурные паттерны, коммуникации и данные

Стиль — общая топология системы. **Паттерн** — повторяемое решение определённой проблемы в конкретном контексте. Одна система может быть модульным монолитом и использовать outbox; другая — микросервисной и комбинировать HTTP, события и CQRS.

- [Коммуникации, контракты и границы данных](communications-and-data.md)
- [Транзакции, саги, повторные доставки](transactions-and-sagas.md)

## Главные вопросы

1. Кто является владельцем факта?
2. Нужно ли потребителю знать результат прямо сейчас?
3. Что происходит при задержке, дубликате или потере связи?
4. Как согласовать изменение БД и публикацию сообщения?
5. Что читается, что изменяется и где гарантируется порядок?
6. Как меняется контракт без одновременного релиза всех участников?

## Карта решений

| Проблема | Возможный паттерн | Оговорка |
|---|---|---|
| Синхронный запрос пользователя | Request-response | Временная связанность и таймауты |
| Реакция многих независимых подсистем | Publish/subscribe | Дубликаты, порядок и отладка |
| Дорогая модель чтения | CQRS / materialized view | Цена синхронизации и обновления проекции |
| Изменение БД + событие | Transactional outbox | Требуется relay и идемпотентный consumer |
| Долгая операция через несколько систем | Saga | Компенсации не равны rollback БД |
| Разные корпоративные системы | Anti-corruption layer / adapter | Нужно владение переводом семантики |
| Критическая зависимость от удалённого API | Timeout, circuit breaker, bulkhead | Нужна продуманная семантика отказов |

**Источник:** книга, главы 15, 18 и 20, в частности различия между запросной и событийной моделью, обмен данными, orchestration/choreography и CQRS. Внешние паттерны outbox, bulkhead и т.п. представлены как дополнительные прикладные техники, не как список книги.
