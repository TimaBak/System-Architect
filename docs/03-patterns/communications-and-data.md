# Синхронность, события, API и топология данных

*Тематическая опора: главы 9, 14–15, 18, 20 и 26. Инженерные рекомендации и образцы — самостоятельное расширение.*

## Выбор коммуникации начинается с семантики

Если клиенту нужно прямо сейчас получить проверенный результат, синхронный запрос уместен. Если изменение уже произошло и множество независимых потребителей должны отреагировать, публикация события снижает прямую связанность.

~~~text
Request / response:
Client → Subscription API → result / timeout / error

Event:
Subscription module → SubscriptionActivated
                         ↘ Notifications
                         ↘ Audit
                         ↘ Analytics
~~~

Эти подходы не исключают друг друга. Например, API сначала подтверждает команду, затем внешний процесс получает события и асинхронно выполняет дальнейшие операции.

## Четыре вопроса к контракту

1. **Тип:** команда, запрос или факт-событие?
2. **Время:** ответ требуется немедленно или может появиться позже?
3. **Гарантия:** at-most-once, at-least-once или иной конкретный режим?
4. **Истина:** где хранится каноническое состояние и когда оно считается подтверждённым?

Примеры названий:
- Command: ActivateSubscription — запрос изменения с возможным отказом.
- Query: GetCurrentSubscription — получение состояния.
- Event: SubscriptionActivated — факт свершившегося изменения.

Не называйте команду событием только потому, что она пересылается брокером.

## Версии и эволюция схем

Для REST/API и событий требуется договор о совместимости: можно ли добавлять необязательные поля, когда удалять старые поля, как новые потребители читают старые данные и наоборот. Критично не только имя поля, но и **семантика**. Поле status со значением active не имеет смысла без формального определения состояния.

Пример контракта события, созданный для учебного кейса:

~~~json
{
  "event_id": "evt-82f1",
  "event_type": "subscription.activated",
  "schema_version": 1,
  "aggregate_id": "sub-123",
  "occurred_at": "2026-10-19T00:00:00Z",
  "correlation_id": "op-671",
  "payload": {
    "plan_code": "standard",
    "effective_from": "2026-10-19T00:00:00Z"
  }
}
~~~

В реальном продукте не публикуйте секреты, платёжные реквизиты и лишние персональные данные в широковещательных событиях.

## Data ownership

Если Billing владеет результатами платежей, другой сервис не должен произвольно менять таблицы Billing. Но потребителю может требоваться проекция «платёж подтверждён» — тогда он поддерживает свою модель чтения по согласованному контракту.

Способы интеграции:

| Подход | Когда уместен | Цена |
|---|---|---|
| Синхронный запрос к владельцу | Нужна актуальная проверка | Зависимость от доступности владельца |
| Событие + локальная проекция | Допустима задержка | Отставание и восстановление проекций |
| Общая БД с контролируемым доступом | Монолит/часть сервисного ландшафта | Риск изменения чужих данных |
| Специализированный read API | Стабильная модель внешнего чтения | Управление версиями и запросной нагрузкой |

## CQRS

CQRS разделяет операции **изменения** и **чтения**. Это может быть логическое разделение в одном процессе, а может — разные модели хранения. **CQRS не требует ни микросервисов, ни event sourcing.** Если простая SQL-модель отвечает требованиям, не усложняйте её специально.

## Согласованность и задержки

Для каждой операции определите допустимое окно несогласованности. Публикация события асинхронно означает, что клиент может увидеть «подписка активна» раньше, чем обновится аналитическая проекция. Для бизнес-критичного решения по доступу не используйте потенциально устаревшую аналитику как единственный источник проверки.

## Тестируемые контракты

- Producer сохраняет схему и назначение полей.
- Consumer умеет безопасно прочитать неизвестные дополнительные поля.
- Повтор события не меняет итоговый бизнес-эффект дважды.
- При временной недоступности целевой системы описаны сроки, retry и DLQ.
- Correlation ID связывает процесс сквозь границы.
- Контрактное тестирование запускается до публикации несовместимой версии.

## Когда меняется выбор

Высокая частота запросов не обязательно оправдывает события: сначала проверьте кэш, индексы и необходимую свежесть. Низкая латентность не означает, что нельзя использовать брокер: важна end-to-end задержка конкретного бизнес-сценария.
