# Кейс: система управления подписками и VPN-доступом

**Тип:** учебное проектирование безопасной системы управления услугой. Не утверждение о фактической инфраструктуре Bakunity или какой-либо другой платформы.

Кейс показывает, как разделить **control plane** (управление пользователями, правами, устройствами и конфигурацией) и **data plane** (непосредственная передача сетевого трафика). Технология сетевого протокола, конфигурация серверов и нормативные требования здесь намеренно не предписываются: они зависят от продукта и юрисдикции.

## 1. Предметная область

Предположим, продукт включает: регистрацию, тарифы, подписки, управление устройствами, выдачу/отзыв конфигурации подключения, поддержку и уведомления. Сетевой транспорт выполняется отдельными узлами.

## 2. Самое важное разделение

~~~text
         [ Web / Telegram Mini App ]
                    |
             [ Control API ]
                    |
  [ Identity | Billing | Subscriptions | Devices ]
                    |
             [ Entitlement service ]
                    |
        [ Node registry + provisioning ]
                    |
              [ VPN nodes ]
              (data plane)
~~~

Это концептуальная карта. Наличие отдельного «Entitlement service» не требует отдельного процесса: это может быть модуль единого приложения.

## 3. Владение бизнес-истинами

| Область | Владеет | Не должна делать |
|---|---|---|
| Identity | Идентичность и сессии | Хранить платёжную истину |
| Billing | Факты и статусы оплаты | Самостоятельно решать сетевые политики |
| Subscriptions | Права, тарифный период | Непосредственно конфигурировать сетевой узел |
| Devices | Привязки и жизненный цикл устройств | Выдавать права без проверки подписки |
| Provisioning | Применение разрешённой конфигурации на узлах | Изменять бизнес-состояние подписки |
| Node registry | Здоровье и метаданные узлов | Становиться базой персональных платёжных данных |
| Support | Операционные действия с аудитом | Обходить бизнес-инварианты вручную |

## 4. Главные сценарии качества

- **Ограничение привилегий:** узел получает только необходимые сведения и полномочия.
- **Корректность доступа:** истечение срока, продление и отзыв не допускают противоречивых состояний.
- **Восстанавливаемость:** control plane умеет восстановить желаемую конфигурацию после перезапуска узла.
- **Адаптивность:** нагрузка на data plane не требует монолитного масштабирования всех административных функций.
- **Аудит:** каждое важное изменение права и конфигурации связано с заявкой/действием, но не требует ненужного сбора содержимого пользовательского трафика.

## 5. Desired state vs observed state

Ключевой приём — различать:
- **Desired:** какое состояние доступа положено пользователю согласно бизнес-правилам.
- **Observed:** какая конфигурация реально подтверждена сетевым узлом.

Если узел недоступен, операция смены подписки не должна молча считаться применённой. Provisioning может безопасно повторить доставку, сравнить desired и observed, фиксировать сбой и эскалировать затяжное расхождение.

~~~text
Payment confirmed → Subscription entitlement changed
                          |
                    Desired state
                          |
                  Provisioning queue
                          |
                    Node apply/ack
                          |
                    Observed state
~~~

## 6. Устройства и жизненный цикл

Определите право добавлять устройство, лимиты активных устройств, отзыв старого, конфликт одновременной регистрации и правило потери связи. Клиентский UI не должен становиться единственным источником истины о действующем доступе.

## 7. Безопасность и эксплуатация

- Проверка идентичности и авторизации админских вызовов.
- Ротация секретов узлов, минимизация распространения ключевого материала.
- Канал управления с защитой от несанкционированного изменения.
- Аудит команд и их результата без избыточной персональной телеметрии.
- Наблюдаемость изменения желаемой/фактической конфигурации.
- Отдельные failure domains для control и data plane, где этого требуют свойства.

**Реальные юридические требования** к сети, данным и идентификации нужно изучать для конкретной страны; этот учебный кейс не заменяет правового анализа.

## 8. С чего начать

Если команда мала, control plane может быть модульным монолитом; работа с узлами выполняется идемпотентными фоновыми заданиями. Отдельные узлы data plane естественно находятся вне главного процесса. При дальнейшем росте разнесение Billing, provisioning и node management зависит от эксплуатационных требований и состава команд, а не от моды на микросервисы.

## 9. Минимальные ADR

1. Источник истины о правах доступа.
2. Модель desired/observed и правила reconciliation.
3. Разделение control/data plane и полномочий.
4. Схема работы с устройствами и токенами.
5. Реакция на потерю связи с узлом и rollback изменений.
