# Кейс: SaaS-платформа с подписками и платежами

**Статус:** учебная архитектура. Не описание существующего продукта. Образец применяет принципы из глав 4–8, 11, 15, 18–22 книги и дополняет их собственными проверками.

## 1. Контекст и предположения

Маленькая команда создаёт SaaS с регистрацией, платными тарифами, кабинетом, поддержкой и уведомлениями. Приоритет — безопасный старт, корректное управление доступом и возможность добавлять новые возможности. Независимые релизы десятков команд не требуются.

Все численные значения по нагрузке, цене и SLO **неизвестны** — их должен предоставить владелец продукта.

## 2. Критичные свойства

1. **Корректность платёжного факта:** один внешний идентификатор успешного платежа не должен создавать дублирующее право доступа.
2. **Восстановление:** оператор может выявить и исправить рассинхронизацию с платёжным провайдером.
3. **Развёртываемость:** новая функция выпускается с контролируемым rollback и миграцией схемы.
4. **Безопасность:** каждый запрос на права проверяется сервером; клиентские признаки не считаются источником истины.
5. **Наблюдаемость:** видно, почему конкретная подписка находится в конкретном состоянии.

## 3. Начальная конструкция

**Гипотеза:** модульный монолит + фоновые workers для отложенной обработки. Причина — малая команда, низкая дополнительная операционная цена и удобные локальные транзакции.

~~~text
[ Web / Mini App ]
          |
       [ API ]
          |
[ Accounts | Plans | Subscriptions | Billing | Support ]
          |
[ governed relational database ]
          |
[ Outbox → Worker → Notifications / external systems ]
          |
[ Metrics / logs / audit ]
~~~

Это не схема обязательного стека. Если данные показывают высокий самостоятельный bottleneck, выбранную границу можно пересмотреть.

## 4. Владение данными

| Модуль | Канонический факт | Что запрещено |
|---|---|---|
| Accounts | User identity / profile | Подмена server-side identity данными клиента |
| Plans | Версионированные условия тарифов | Молчаливое изменение условий действующего договора |
| Billing | PaymentAttempt / provider reference | Сторонняя запись «успешно оплачен» без верификации |
| Subscriptions | Состояние подписки и права | Повторное продление одним и тем же фактом |
| Notifications | Доставка сообщений | Считать отправку письма подтверждением платежа |

## 5. Последовательность оплаты

1. API создаёт локальный заказ с устойчивым business ID.
2. Billing отправляет запрос к провайдеру с поддерживаемым идемпотентным ключом, если провайдер допускает такой режим.
3. Подтверждение поступает через защищённый callback или серверную сверку.
4. Billing проверяет подлинность, идентичность события и допустимые переходы состояния.
5. Subscriptions получает подтверждённый факт и применяет право **ровно один раз как бизнес-эффект**.
6. В ту же локальную транзакционную область пишется событие для последующих реакций, если применим outbox.
7. Notifications пытается доставить сообщение, не определяя судьбу платежа.

### Отказные сценарии

| Сбой | Ожидаемая реакция |
|---|---|
| Callback пришёл дважды | Второй не меняет подписку |
| API провайдера недоступен | Заказ остаётся в определённом промежуточном состоянии |
| Событие уведомления не обработано | Retry, DLQ, диагностируемый статус |
| Приложение упало после сохранения состояния | Worker дочитывает outbox |
| Пользователь отключил устройство | Права сохраняются в серверной модели независимо от UI |
| Схема БД меняется | Обе версии кода совместимы на период миграции |

## 6. Архитектурные решения

- ADR-001: модульный монолит на первом этапе (общий релиз оправдан).
- ADR-002: Billing является источником истины по обработанным внешним платёжным фактам.
- ADR-003: права предоставляются по проверенному событию с защитой от повторов.
- ADR-004: фоновые операции не блокируют критический пользовательский ответ без необходимости.
- ADR-005: новые доменные зависимости проходят автоматический тест архитектуры.

Каждый ADR обязан содержать альтернативы и условия пересмотра.

## 7. Метрики без выдуманных нормативов

Определите и измеряйте: процент ошибочных переходов, возраст необработанных платежных событий, задержку активации, успешность сверки, p95 критического API, recovery time, частоту откатов релиза.

## 8. Когда выделять сервис

Если Billing получает отдельную команду, особые требования безопасности или независимый жизненный цикл; либо если выделение снимает **измеренный** локальный bottleneck — сервисная архитектура может быть оправданна. До этого доменные границы следует обеспечить внутри монолита.
