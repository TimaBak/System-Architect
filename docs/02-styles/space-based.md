# Архитектура на основе пространства (Space-based)

**Источник:** глава 16, стр. 313–345.

## Идея

Убрать постоянно перегруженное централизованное хранилище из критического пути каждого запроса, используя **распределённые блоки обработки и сетку данных в памяти**. Система может адаптировать число processing units под переменную нагрузку.

~~~text
             [ Load / message distribution ]
                 /           |           \
          [ Worker A ]   [ Worker B ]   [ Worker C ]
             ↕              ↕              ↕
           [ partitioned / replicated data grid ]
                           ↓
                 [ asynchronous data persistence ]
~~~

Это не просто «положить Redis перед базой». У архитектуры есть собственные решения о владении, репликации, согласованности, обработке и записи данных.

## Устройство

- **Processing units:** единицы обработки, которые могут масштабироваться.
- **Messaging grid:** доставка вызовов или сообщений к единицам.
- **Data grid:** локальность, репликация и размещение актуальных данных.
- **Processing grid:** координация обработки.
- **Deployment manager:** регулирование состава исполнителей.
- **Data pumps / readers / writers:** связи с внешним постоянным хранением.

Названия отражают элементы главы 16; конкретные технологии не предписаны.

## Почему помогает при пиках

Запросы не обязаны каждый раз конкурировать за один сервер БД. Данные можно расположить ближе к обработке, а capacity увеличивать по нужной оси. Но свойства зависят от объёма памяти, особенностей разделения данных и семантики записи.

## Основные риски

1. **Согласованность реплик:** несколько экземпляров могут видеть разные состояния.
2. **Коллизии записей:** два исполнителя обновляют связанную сущность.
3. **Потеря/задержка записи:** подтверждение в памяти не равно долговечному сохранению.
4. **Размер рабочего набора:** не все данные разумно держать в памяти.
5. **Сложное восстановление:** следует проверить перераспределение партиций после отказа узлов.
6. **Операционная стоимость:** observability и тестирование отказов сильно сложнее обычной БД.

## Когда кандидат

Очень высокий, непредсказуемый всплесковый поток запросов, который плохо обслуживается традиционным узким местом записи/чтения. Требуется доказательство нагрузкой и расчётом затрат.

## Когда отказаться

Если нагрузка умеренная или данные требуют строгих транзакций через широкий набор сущностей, распределённая сетка может создать гораздо больше проблем, чем решить. Сначала измерьте и оцените более простые альтернативы: индексирование, read replicas, caching, partitioning, batching.
