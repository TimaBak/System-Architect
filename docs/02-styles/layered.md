# Многоуровневая архитектура (Layered)

**Первичный источник:** глава 10, стр. 177–189. Схемы и кейс ниже разработаны для справочника.

## Идея

Разделить приложение на уровни **по технической ответственности**, обычно UI → бизнес-логика → сохранение данных → хранилище. Число уровней, их физическое размещение и порядок вызовов зависят от реализации.

~~~text
[ Presentation / HTTP / UI ]
             ↓
[ Business logic / services ]
             ↓
[ Persistence / repositories ]
             ↓
[ Database / file storage ]
~~~

**Важно:** логический уровень не обязательно означает отдельный процесс или сервер. Четыре слоя могут работать внутри одного приложения.

## Закрытые и открытые уровни

**Закрытый слой** запрещает обход себя при движении запроса. Это обеспечивает контроль и предсказуемую точку применения политик. **Открытый** разрешает пересечение границы, что иногда уменьшает ненужные вызовы. Но если открывать всё подряд, структура теряет смысл.

Пример: UI не должен писать прямо в БД, минуя проверку бизнес-инвариантов. При этом чтение справочника может использовать специализированный путь без прохождения всех доменных операций — если такой обход явно спроектирован.

## Данные и транзакции

Типичная реализация — общая реляционная БД и локальные ACID-транзакции для бизнес-операций. Это упрощает поддержание целостности, но при разрастании схемы и кода усиливает связанность. Разграничивайте доступ к таблицам, даже если физически хранилище одно.

## Где сильна

- Небольшие приложения с хорошо понятными сценариями.
- Команды с ограниченным временем на инфраструктуру.
- Системы, для которых простота создания и эксплуатации важнее независимых релизов предметных областей.
- Приложения, где пользователи выполняют относительно линейные бизнес-операции.

## Цена выбора

- Уровни меняются совместно; даже малая функция может задеть UI, сервис, persistence и БД.
- Высокая связанность по развертыванию: часто выпускается весь артефакт.
- Масштабирование обычно затрагивает значительную часть приложения, а не один доменный участок.
- Лишние пересылки по уровням ухудшают понимание потока и могут бить по производительности.
- Плохое разделение бизнес-правил приводит к «анемичным» сервисам и смешению ответственности.

## Учебный кейс

**Внутренний портал заявок** с десятками сотрудников и одной небольшой командой. Многоуровневая архитектура может обеспечить низкие издержки сопровождения. Однако если обработка заявок и аналитика начинают развиваться независимо, стоит рассмотреть предметные модули или сервисную декомпозицию.
