# II. Архитектурные стили: сравнительная карта

Стили задают типичную топологию приложения, границы развертывания, взаимодействие компонентов и организацию данных. Это **отправные точки проектирования**, а не готовые рецепты.

Второе издание Ричардса и Форда рассматривает девять стилей в главах 10–18. Каждый материал этого раздела имеет одинаковую рамку: устройство → данные и взаимодействия → достоинства → цена и риски → применимость → пример → вопросы для ревью.

## Девять стилей

| Стиль | Организующий принцип | Частый выигрыш | Главная цена |
|---|---|---|---|
| [Многоуровневая](layered.md) | Технические уровни | Понятная структура и простая разработка | Прохождение многих слоёв, низкая изоляция предметных функций |
| [Модульный монолит](modular-monolith.md) | Изолированные доменные модули в одном развёртывании | Простая эксплуатация при хороших границах | Общий релиз и риск нарушения изоляции |
| [Конвейерная](pipeline.md) | Последовательность фильтров обработки | Композиция этапов | Формат сообщений и ошибки между этапами |
| [Микроядерная](microkernel.md) | Ядро и расширения-плагины | Настраиваемость | Стабильность API плагинов |
| [На основе сервисов](service-based.md) | Небольшое число крупнозернистых сервисов | Независимость частей без полной микросервисной цены | Координация, общие данные и контракты |
| [Событийная](event-driven.md) | Продюсеры, события и потребители | Развязка во времени | Отладка, порядок, ошибки, eventual consistency |
| [На основе пространства](space-based.md) | Распределённая сетка данных и обработки | Выдерживание экстремальных пиков | Согласованность и сложность state management |
| [Оркестрированная SOA](orchestrated-soa.md) | Общий сервисный ландшафт и координация | Интеграция сложной корпоративной среды | Центральная сложность и высокая связанность |
| [Микросервисы](microservices.md) | Небольшие автономные доменные сервисы | Независимое изменение и масштабирование частей | Распределённая операционная сложность |

**Оговорка:** таблица не переводит качественные оценки авторов в универсальные баллы. Свойства меняются от конкретной реализации, зрелости команды и требований бизнеса.

## Как выбирать на практике

### Когда нужно быстро построить первый продукт

Сначала проверьте, хватает ли **модульного монолита**. Независимое развёртывание каждого компонента может не окупить стоимость инфраструктуры, отладки, контрактов и обработки сбоев.

### Когда масштабируется отдельная бизнес-область

Оцените **сервисную архитектуру** или выделение одного сервиса из монолита. Не требуется делить всё приложение сразу.

### Когда действия не должны ждать друг друга

**Событийные взаимодействия** могут дополнять любой стиль. Не делайте вывод, что появление очереди автоматически превратило монолит в событийную архитектуру.

### Когда нужен рынок плагинов или кастомизация

**Микроядро** полезно, если большая часть системы стабильна, а дополнительные возможности меняются через контракты расширений.

### Когда цель — обработка потока

**Конвейер** естественен для ETL, разбора файлов, последовательной нормализации.

### Когда система попадает под непредсказуемые экстремальные пики

**Пространственная архитектура** может быть кандидатом, если архитектура данных и стоимость памяти оправданы. Она не является обязательным решением для любой высоконагруженной системы.

### Когда много самостоятельных продуктовых команд

**Микросервисы** могут локализовать изменения, если команды действительно способны владеть полным жизненным циклом своих сервисов, включая эксплуатацию.

## Матрица вопросов, без которой сравнение бессмысленно

| Вопрос | Почему важен |
|---|---|
| Какие 3 свойства системы критичны? | Выбор оптимизируется не по всем осям сразу |
| Кто владеет данными и инвариантами? | Определяет стоимость распределённых транзакций |
| Нужны ли независимые релизы? | Один из главных драйверов сервисной декомпозиции |
| Есть ли зрелая эксплуатация и on-call? | Распределённость переносит стоимость в ops |
| Какой ожидается рост и где bottleneck? | Разделяем по измеренным ограничениям |
| Как будут тестироваться сбои? | Сложность = не только штатный путь |
| Кто отвечает за контракты API/событий? | Изменение контракта становится организационной задачей |
| Сколько времени допустимо тратить на инфраструктуру? | Имеет прямую бизнес-цену |

## Частые ложные противопоставления

- «Монолит» не означает «спагетти». Плохо устроенный монолит и модульный монолит — разные вещи.
- «Микросервисы» не означают автоматическую масштабируемость и устойчивость.
- «Общая БД» не всегда запрещена, но общий доступ на запись требует явного контроля.
- «Асинхронность» не гарантирует доставку, порядок и отсутствие потерь.
- «Архитектура на событиях» может сочетаться с сервисами и модульным монолитом.
