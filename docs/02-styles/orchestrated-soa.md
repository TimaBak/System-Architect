# Оркестрированная сервис-ориентированная архитектура (Orchestrated SOA)

**Источник:** глава 17, стр. 346–361.

## Идея

Стиль типичен для сложных корпоративных интеграций: отдельные виды сервисов, общая интеграционная инфраструктура и **механизм оркестрации**, координирующий бизнес-процессы.

~~~text
[ Business-facing services ]
              ↓
[ Workflow / orchestration ]
              ↓
[ Enterprise integration layer ]
       /        |         \
[ App A ]    [ App B ]    [ Legacy C ]
~~~

В главе обсуждается исторический контекст этого подхода, в котором высокая переиспользуемость сервисов может усилить связанность между подразделениями.

## Сильные стороны

- Централизованное управление сложными сквозными процессами.
- Интеграция нескольких существующих корпоративных систем.
- Возможность согласовать корпоративные контракты и требования.
- Единые политики доступа и аудита, если ими не злоупотреблять.

## Цена

- Центр оркестрации может концентрировать бизнес-логику, стать bottleneck и общей точкой отказа.
- Канонические модели предприятия трудны для развития: при общем контракте изменение одного отдела затрагивает другие.
- Бизнес-операции могут проходить через множество слоёв.
- Высокая стоимость координации команд и административного контроля.
- Попытка повторно использовать всё ведёт к связанности вместо независимости.

## Кейс: консолидация страховок

У компании несколько исторических систем расчёта, кабинетов и проверок. Требуется сквозной бизнес-процесс без одновременного переписывания legacy. Оркестрация может дать управляемый промежуточный этап. Однако вся новая бизнес-логика не должна автоматически переезжать в центральную шину.

## Как уменьшать риск

- Явно ограничьте роль оркестратора: он координирует, а не владеет всем доменом.
- Вводите версионирование контрактов.
- Минимизируйте глобальную каноническую модель.
- Разделяйте бизнес-контракты и интеграционные адаптеры.
- Измеряйте критический путь и зависимости по доступности.
- Фиксируйте план постепенного вывода устаревших интеграций.

3. Как быстро найти отказ внутри длинного процесса?
4. Как пережить недоступность orchestration engine?
5. Есть ли оправдание для централизованной платформы в масштабе компании?
