# Микросервисная архитектура (Microservices)

**Источник:** глава 18, стр. 362–390.

## Идея

Система разделяется на **автономные предметные сервисы**, у каждого — собственная ответственность, контракты, жизненный цикл и контролируемое владение состоянием. В книге ключевым понятием является **bounded context**: независимость важнее количества строк в сервисе.

~~~text
           [ API / client gateways ]
              /       |         \
    [ Accounts ] [ Subscriptions ] [ Billing ]
        ↓               ↓               ↓
    Own state       Own state       Own state
          <--- explicit API / events --->
~~~

«Небольшой» не значит «сервис на один CRUD endpoint». Границу определяют доменные инварианты и автономия изменения.

## Отличительные решения

- **Владение данными:** прямые записи в чужое хранилище обычно недопустимы.
- **Доступ к API:** сервисные контракты и клиентский слой не должны случайно создавать монолитный gateway.
- **Сеть:** каждый вызов имеет задержку и режим отказа.
- **Развёртывание:** независимость требует автоматизации, совместимых миграций и разведения релизных циклов.
- **Команды:** владение сервисом включает поддержку в эксплуатации.
- **Общие компоненты:** допустимы операционные инструменты, но общий доменный пакет может синхронизировать все релизы.
- **Транзакции:** локальные операции плюс явное управление распределёнными бизнес-процессами.

## Неизбежные дополнительные задачи

| Задача | Почему возникает |
|---|---|
| Timeout/retry/circuit breaker | Частичные сетевые отказы |
| Tracing + correlation ID | Один пользовательский запрос пересекает процессы |
| Idempotency | Повторные вызовы и доставки |
| API/schema evolution | Разные версии клиентов и сервисов живут одновременно |
| Service identity / authz | Не каждый внутренний вызов доверенный |
| Migration strategy | Невозможно атомарно обновить все БД и процессы |
| SLO + alerting | Иначе независимость не подтверждается операционно |
| Local/contract/integration tests | Один unit-test не доказывает работу цепочки |

## Где оправдано

Разные домены меняются независимо, есть несколько продуктовых команд, измеренные требования к независимому масштабированию или отказной изоляции и организация готова оплачивать распределённую эксплуатацию.

## Где может навредить

Маленькая команда с неустойчивыми границами продукта, жёстким временем выхода в релиз и отсутствием зрелых CI/CD и наблюдаемости. Распилить код легко; договориться о данных и процессах сложнее.

## Переход из модульного монолита

1. Измерьте реальную стоимость существующей связанности.
2. Выберите модуль с устойчивой бизнес-границей и отдельной потребностью.
3. Введите контракт в монолите; добейтесь тестируемой изоляции.
4. Подготовьте владение данными и стратегию миграции (не «двойная запись на авось»).
5. Примените постепенный перенос трафика и контролируемый rollback.
6. Пересмотрите SLO, бюджет эксплуатации и обязанности команды.
7. Только затем рассмотрите следующий кандидат на выделение.

## Пример сбоя

Операция заказа синхронно вызывает пять сервисов. Даже если каждый обычно доступен, интегральная цепочка может сбоить чаще; ретраи при перегрузке могут усилить каскад. Решайте это границами пользовательской операции, допустимой деградацией и ограничением зависимостей, а не только «добавить Kubernetes».

## Вопросы ревью

- Может ли сервис выпускаться без синхронной миграции всех других?
- Есть ли у него собственная модель, а не CRUD-фасад над общей таблицей?
- Сколько синхронных hop на критическом пути?
- Кто отвечает за межсервисные инварианты?
- Что реально происходит при недоступности любого соседа?
- Можно ли доказать пользу распределённости цифрами и процессом разработки?
