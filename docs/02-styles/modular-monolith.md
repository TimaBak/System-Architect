# Модульный монолит (Modular Monolith)

**Источник:** глава 11, стр. 190–204. Раздел об исходных границах и контроле связанности перекликается с главами 3 и 8.

## Идея

**Один основной артефакт развёртывания, несколько строго разделённых предметных модулей.** В отличие от классической многоуровневой схемы, главная структурная ось — *области бизнеса*, а не общая лестница Controller → Service → Repository.

~~~text
               [ HTTP/UI ]
                   |
             [ Application ]
       /           |            \
[ Accounts ] [ Subscriptions ] [ Billing ]
    API            API            API
      \            |             /
           [ controlled DB ]
~~~

В каждом модуле могут быть собственные прикладной, доменный и инфраструктурный слои. Один процесс не делает систему немодульной; отдельные папки сами по себе не создают модульности.

## Как создать настоящие границы

- Каждый модуль владеет определёнными инвариантами и областью модели.
- Внешние модули используют только опубликованные API, не внутренние классы.
- Запретите циклические импорты и обходной доступ к данным.
- Публикуйте предметные события, когда асинхронность действительно нужна; не превращайте каждый локальный вызов в очередь.
- Проверьте границы на реальной истории изменений, а не только по красивой карте.
- Измеряйте и автоматически проверяйте архитектурные ограничения.

Пример проекта:

~~~text
src/
  accounts/{api,domain,infra}
  subscriptions/{api,domain,infra}
  billing/{api,domain,infra}
  application/{http,bootstrap}
tests/architecture/
~~~

Это иллюстрация; технология языка и сборки может быть любой.

## Данные: одна БД не означает общую модель

Возможна общая физическая БД, но желательно **логическое владение схемами/таблицами** и запрет чужих записей. Иначе изменение Billing меняет внутренности Subscriptions без контракта.

Локальные транзакции часто остаются преимуществом модульного монолита. Вместе с тем нужно осознанно проектировать сообщения внешним системам: транзакция БД не делает доставку webhook или email атомарной.

## Преимущества

- Небольшие операционные расходы, простая локальная отладка.
- Хорошие границы ответственности без распределённых вызовов на каждый шаг.
- Возможность начать с малого и извлекать самостоятельные сервисы при доказанной необходимости.
- Понятная организация предметных команд при дисциплине владения.

## Ограничения

- Основной релиз общий; ошибка в одном модуле потенциально влияет на процесс целиком.
- Бесконтрольный рост shared/common быстро уничтожает границы.
- Масштабирование одной части отдельно от остальных сложнее.
- Для крупных команд возникает давление на автономию выпуска функций.
- Слабый CI не заметит скрытую деградацию модульности.

## Когда выбрать

Хорошая стартовая гипотеза для продукта с неопределёнными требованиями, небольшими командами и ограниченным бюджетом. Это совпадает с общей рекомендацией главы 11 о прагматичном старте, **но не является правилом для всех систем**.

## Когда эволюционировать

Сигналы: действительно независимые команды и циклы выпуска; измеренный локальный bottleneck; разные операционные SLO; отдельные требования изоляции и безопасности. Выделяйте одну подтверждённую границу, а не «разрезайте по таблицам».

## Проверка

1. Проводятся ли тесты на запрещённые зависимости?
2. Кто имеет право записи в данные модуля?
3. Сколько файлов меняется при добавлении одного бизнес-правила?
4. Можно ли вынести модуль в процесс без переписывания предметной логики?
5. Зачем нам *именно сейчас* отдельный релиз этого модуля?

**Сравнить:** [многоуровневая](layered.md), [сервисная](service-based.md), [микросервисы](microservices.md).
