# Микроядерная архитектура (Microkernel / Plug-in)

**Источник:** глава 13, стр. 218–234.

## Идея

Стабильное **ядро** реализует базовые возможности, а переменная функциональность добавляется подключаемыми компонентами — плагинами. Типичные области: настольные приложения, IDE, конструкторы, платформы с расширениями под заказчика.

~~~text
              [ Core / registry ]
                /     |      \
         [ Plug-in A ][ B ][ Plug-in C ]
                  versioned contracts
~~~

Наличие слова «микро» не связывает этот стиль с микросервисами. Плагины могут выполняться в том же процессе, а могут общаться с ядром удалённо.

## Границы ядра

Ядро должно предоставлять жизненный цикл плагинов, контракты, разрешения и базовые гарантии продукта. Если поместить всю бизнес-логику в ядро, расширять систему станет трудно. Если ядро слишком мало, плагины начнут зависеть друг от друга напрямую.

## Дизайн контрактов

- Публичный SDK и семантическая совместимость.
- Регистрация, активация, отключение и обновление расширений.
- Модель данных и собственные миграции.
- Безопасность: какие возможности плагин вправе вызывать.
- Схема обработки ошибок и ограничения ресурсов.
- Отзыв несовместимого или небезопасного плагина.
- Способ тестирования расширения вне полной системы.

**Ключевой риск:** плагин, выполняющийся в общем процессе с полными правами, может обрушить ядро или получить доступ к чужим данным. Для непроверенных расширений рассмотрите изоляцию процесса, sandbox или удалённое выполнение — за стоимость межпроцессной коммуникации.

## Когда подходит

Клиенты требуют различных функций, рынок дополнений важен, платформа должна расширяться без постоянной правки общей кодовой базы.

## Когда не подходит

Если разные клиентские потребности затрагивают сами инварианты ядра, модель расширений становится хрупкой. Если важна независимая отказоустойчивость каждого домена, одного общего ядра может быть недостаточно.

## Учебный пример

У системы проверки документов есть ядро «загрузить → проверить политику → сохранить результат». Плагины предоставляют адаптеры форматов и дополнительные проверки. **Архитектурное решение:** расширение не вправе напрямую править базовые пользовательские записи.

## Проверка

1. Как без остановки платформы обновить один плагин?
2. Какие версии ядра с ним совместимы?
3. Возможна ли утечка данных через API расширений?
4. Кто подписывает и проверяет пакет плагина?
5. Как устраняются зависимости между плагинами?
