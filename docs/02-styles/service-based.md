# Архитектура на основе сервисов (Service-based)

**Источник:** глава 14, стр. 235–253.

## Идея

Приложение делится на **относительно небольшое количество крупных предметных сервисов**, которые могут развертываться независимо. В отличие от микросервисов с более мелкими границами, здесь часто сохраняют более широкие бизнес-транзакции внутри сервиса и допускают разные топологии хранения данных.

~~~text
[ Web / Mobile ] → [ API / Routing ]
                          |
               +----------+---------+
               |          |         |
            Accounts    Orders    Billing
               |          |         |
            owned or governed data topology
~~~

Глава 14 описывает стиль как прагматичный гибридный подход, в котором распределённость присутствует, но её сложность ниже, чем при множестве микросервисов.

## Модель данных

Варианты: общая БД с правилами владения или выделенные хранилища сервисов. Нельзя делать вывод, что отдельный сервис автоматически имеет отдельную БД; однако общий доступ к данным может создавать высокую статическую и динамическую связанность.

Если сервисы делят таблицы и независимо мигрируют, выпуск каждого превращается в согласованный релиз — это разрушает ожидаемую автономию.

## Плюсы

- Более независимые циклы выпуска по крупным доменам.
- Возможность по-разному масштабировать нагруженные части.
- Меньше распределённых взаимодействий, чем в слишком мелкой микросервисной системе.
- Более понятная привязка сервисов к командам.

## Цена

- Появляются сетевые сбои, таймауты и версионирование API.
- Потребуются наблюдаемость, маршрутизация, защита сервисных вызовов.
- Сложность хранения и транзакций зависит от пересечения доменных границ.
- Крупный сервис может со временем стать «вторым монолитом» без внутренней модульности.

## Когда выбирать

Есть чёткие бизнес-поддомены и реальная потребность выпускать их отдельно, но нет достаточных причин превращать каждую маленькую функцию в сервис.

## Переход из монолита

1. Найдите модуль с устойчивой границей.
2. Выделите публичный контракт и приведите данные к контролируемому владению.
3. Замерьте вызовы и устраните неявные shared-state зависимости.
4. Подготовьте журналирование, мониторинг, retry/timeout, rollback.
5. Перенесите только выбранную область, не пытайтесь всё распилить одновременно.

## Проверка

- У каждого сервиса единая ответственность, а не техническая роль?
- Есть ли непроизвольные распределённые транзакции между сервисами?
- Кто и как ведёт миграции общих таблиц?
- Реально ли команды выкатываются независимо?
- Есть ли отдельные SLO и дежурство, если этого требует бизнес?
