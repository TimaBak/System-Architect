# Событийная архитектура (Event-Driven Architecture)

**Источник:** глава 15, стр. 254–312. Дополнения по идемпотентности и outbox — самостоятельные инженерные примеры.

## Идея

Значимые **факты об уже случившемся** публикуются как события; разные обработчики могут реагировать на них без обязательного прямого вызова друг друга.

~~~text
[ Order ]
    | OrderPlaced
    v
[ Broker ] --> [ Payment handler ]
         \--> [ Notification handler ]
         \--> [ Analytics projection ]
~~~

**Событие** («подписка активирована») не то же самое, что **команда** («активируй подписку»). Первая формулировка сообщает факт, вторая требует действия. Способ доставки сам по себе не превращает команду в событие.

## Две важные топологии

**Broker:** участники публикуют и потребляют сообщения, общий координатор бизнес-процесса может отсутствовать. Выигрыш — слабее временная связанность и легче добавление реакций. Цена — труднее получить сквозной статус и обработать исключительные ветви.

**Mediator:** выделенный координатор следит за шагами процесса и посылает команды исполнителям. Выигрыш — видимый ход долгой операции и управление ошибками. Цена — центр управления может стать узким местом и местом логической связанности.

Гибрид допустим: важна явная ответственность за бизнес-процесс.

## Топология данных

Варианты: общая БД, доменные хранилища, специализированные проекции. События не снимают вопрос «кто владеет правдой». Хранение события и бизнес-изменения должно быть согласовано, иначе возникает «данные сохранились, событие потерялось».

## Отказные сценарии, которые надо спроектировать

| Сценарий | Нужное решение |
|---|---|
| Сообщение доставлено дважды | Идемпотентный consumer и уникальный ключ |
| Consumer недоступен | Очередь хранения, повторные попытки и политика DLQ |
| Сообщения пришли не по порядку | Версионирование состояния, ключ порядка, защита от старых данных |
| Producer сохранил данные, но не отправил событие | Transactional outbox или другой согласованный механизм |
| Очередь выросла | Backpressure, квоты, горизонтальное масштабирование с замерами |
| Изменился формат события | Схемы, совместимые контракты, эволюция потребителей |
| Долго не приходит финальный результат | Наблюдаемый workflow и правила эскалации |

**Гарантия exactly-once** требует точного определения границы и побочных эффектов. «Брокер обещает exactly-once» ещё не значит, что внешний платёж или письмо не будет выполнено повторно.

## Где стиль помогает

Обработка разных независимых последствий одного действия; потоки данных; интеграции с неравномерной нагрузкой; системы, где обработка может быть отложенной.

## Где дорого

Сценарии, требующие мгновенного синхронного ответа; длинные процессы со множеством компенсирующих операций; команды без наблюдаемости и дисциплины схем.

## Мини-кейс

Пользователь оплатил подписку. Billing фиксирует платежный факт; Subscriptions переводит состояние по согласованным правилам; Notifications доставляет сообщение. Сложность — не три коробки, а дубликаты, сбои и восстановление состояния между этапами.

## Вопросы ревью

1. У события есть владелец, версия, корреляционный ID?
2. Явно ли описан контракт «как минимум один раз / максимум один раз»?
3. Где сохраняются необработанные события, что такое poison message?
4. Как заметить зависшую подписку и кто исправит её?
5. Когда следует предпочесть явную оркестрацию вместо бесконтрольной хореографии?
