# Модульность, связность и зависимости

*Книга: глава 3. Ниже — самостоятельные примеры и прикладные эвристики.*

## Термины, которые нельзя путать

- **Модульность:** разбиение системы на части с понятной ответственностью.
- **Связность внутри модуля (cohesion):** насколько принадлежащие ему элементы решают единую задачу.
- **Связанность между модулями (coupling):** насколько изменение одного влияет на другие.
- **Гранулярность:** размер и количество модулей или сервисов.
- **Коннасценция (connascence):** необходимость для элементов меняться согласованно из-за общего знания или соглашений.

Хорошая архитектура стремится к высокой предметной связности *внутри* границы и контролируемой связанности *между* границами. Однако не пытайтесь минимизировать все зависимости любой ценой: чрезмерные абстракции сами увеличивают сложность.

## Пример плохой границы

~~~text
Controllers → Utils → GeneralService → CommonModels
      ↘           ↗          ↑            ↖
        Billing ───────────────┘          Accounts
~~~

Название GeneralService не объясняет ответственность. CommonModels может стать скрытой общей моделью данных, изменение которой задевает всех.

## Улучшение через предметные модули

~~~text
[Accounts]     [Subscriptions]     [Billing]
   owns             owns             owns
 Account          Subscription      PaymentAttempt
      \             |               /
       \--- explicit contracts ------/
~~~

Здесь «owns» означает **ответственность за инварианты и изменения**, а не требование отдельной физической базы данных. В монолите модули могут храниться в одной СУБД, но не должны бесконтрольно писать в чужие таблицы.

## Измерение связанности

В главе 3 рассматриваются входящие и исходящие зависимости, абстрактность и нестабильность. Одна из часто используемых метрик — **I = Ce / (Ca + Ce)**, где **Ce** — число исходящих зависимостей, **Ca** — входящих. При нулевом знаменателе значение требует отдельного определения, не подставляйте фиктивную стабильность.

Метрика **D = |A + I − 1|** измеряет удалённость от «главной последовательности», где A — доля абстрактности, I — нестабильность. Она не заменяет смысловой анализ: архитектурно ошибочный модуль вполне может иметь красивые числа.

Практическая интерпретация:

- Много входящих зависимостей: изменение интерфейса затронет множество потребителей.
- Много исходящих зависимостей: компонент труднее тестировать и менять изолированно.
- Низкая предметная связность: компонент, возможно, содержит несколько причин для изменения.
- Циклы зависимостей: опасность невозможности независимого изменения и тестирования.

## Способы управления

1. **Зависимости только в допустимом направлении.** Domain не должен импортировать delivery-слой.
2. **Публичные API модулей.** Остальные внутренние типы не обещают стабильности.
3. **Владение данными.** Нельзя создавать обходные записи в таблицы другого модуля.
4. **Архитектурные тесты.** Проверка циклов, запрещённых импортов, размерности публичного API.
5. **Контрактные изменения.** Сначала совместимое расширение, затем миграция потребителей, затем удаление устаревшего поля.
6. **Командное владение.** Должно быть ясно, кто одобряет изменение границы.

## Когда НЕ дробить дальше

Если двум функциям нужны одни и те же транзакционные инварианты и они постоянно меняются вместе, разделение на удалённые сервисы может создать распределённую транзакцию без выигрыша. Сначала проверьте бизнес-границы и требования к независимому развертыванию.

## Чек-лист ревью

- Могу ли я описать ответственность модуля одним абзацем?
- Какие данные он считает своей истиной?
- Кто вправе изменять его состояние?
- Изменение в нём требует правок в нескольких несвязанных модулях?
- Можно ли запретить неподходящие зависимости автоматически?
- Есть ли циклы и общий пакет, ставший центром всего?
- Не скрываем ли общий runtime за видимостью независимости?

**Упражнение:** выпишите десять последних изменений приложения. Разложите их по модулям. Если большинство изменений регулярно трогает одни и те же пары модулей, это повод пересмотреть границы.
