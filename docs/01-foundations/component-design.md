# От требований к логическим компонентам

*По главе 8 книги: компонентно-ориентированное мышление. Процедура и предметный пример — самостоятельные.*

## Логические ≠ физические границы

**Логический компонент** объединяет правила и операции определённой ответственности. Он может быть реализован как модуль в монолите, отдельный сервис, библиотека или комбинация механизмов. Сначала выделите ответственность; физическую топологию выбирайте с учётом свойств системы.

## Практическая последовательность

### 1. Соберите сценарии

Опишите действия пользователей и операторов в терминах домена: «оформить подписку», «сменить тариф», «обработать повторную оплату», «отозвать доступ». Не начинайте с названий контроллеров и таблиц.

### 2. Найдите обязанности

Группируйте операции, изменяющиеся по одной бизнес-причине: управление тарифами, жизненный цикл подписки, учёт платежей, доставка уведомлений, авторизация доступа.

### 3. Назначьте владельцев инвариантов

Инвариант — утверждение, которое должно оставаться истинным независимо от вызова API. Например, одному входящему уникальному платежному событию соответствует не более одного применения к расчётному состоянию подписки. Укажите, какой компонент охраняет это правило.

### 4. Очертите контракты

~~~text
Billing:
  input: payment-provider callback (verified, idempotent)
  owns: payment_attempt, payment_event ledger
  output: PaymentConfirmed / PaymentRejected
Subscriptions:
  input: PaymentConfirmed
  owns: subscription state, expiration rule
  output: SubscriptionActivated
Notifications:
  input: SubscriptionActivated
  owns: delivery attempts
~~~

Вариант выше — **одна из возможных моделей**; схема не предписывает конкретный брокер, БД или количество процессов.

### 5. Исследуйте зависимости

Кто кому нужен в момент выполнения? Кто может продолжать работу при недоступности другого? Есть ли циклы? Происходит ли случайно синхронное сцепление независимых процессов?

### 6. Уточните границы

Сверьте изменения за прошлые релизы: если компоненты всегда меняются вместе, возможно, граница искусственна. Если компонент хранит несколько независимых бизнес-истин, возможно, он слишком крупный.

## Тест на хорошую границу

- Ответственность выражена в терминах задачи, а не фреймворка.
- Есть понятный источник истины для состояния.
- Внешние потребители видят контракт, но не внутренние структуры.
- Команда способна тестировать локальную логику без полной системы.
- Решения о согласованности приняты явно.
- Ошибки внешних зависимостей не превращают любой сценарий в тотальный сбой.
- Граница оправданна частотой изменений, сложностью домена и нужными свойствами.

## Что делать с общей базой

У разных модулей может быть одна физическая СУБД, но желательно различать владельца таблиц, право записи и механизм интеграции. Отдельная база сама по себе не гарантирует слабую связанность: синхронные цепочки API могут создать ещё более жёсткую связь.

## Два антипаттерна

**Компоненты по техническим слоям:** DatabaseService, DTOService, GenericUtils. Весь бизнес-процесс прыгает между ними, меняются они совместно.

**Компоненты по существительным без инвариантов:** отдельный сервис на каждую таблицу. Это умножает сетевые вызовы и делает локальные транзакции распределёнными.

## Результат этапа

Создайте реестр:

| Компонент | Ответственность | Данные | Вход/выход | Основной риск |
|---|---|---|---|---|
| Subscriptions | Жизненный цикл | Подписка | Commands/events | Неправильный переход состояния |
| Billing | Платёжные факты | PaymentAttempt | Callback, PaymentConfirmed | Повторная обработка |
| Notifications | Доставка сообщений | DeliveryAttempt | SubscriptionActivated | Повторная доставка |
