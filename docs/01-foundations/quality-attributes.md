# Свойства архитектуры: как превратить требования в проверяемые ограничения

*По темам глав 4–7 книги. Значения метрик и примеры ниже — учебные, не выдержки из первоисточника.*

## Функции и качества — разное

**Функциональное требование:** пользователь может оформить подписку.

**Свойство качества:** оформление остаётся корректным при повторном callback от платёжного провайдера, обрабатывается в согласованное время и не теряет подтверждённые результаты при перезапуске приложения.

Авторы выделяют эксплуатационные, структурные, облачные и сквозные свойства. Свойства часто конкурируют: например, усиление синхронной согласованности усложняет географическую доступность; повышенная изоляция улучшает отказоустойчивость, но увеличивает цену интеграции.

## Каталог для первого анализа

| Свойство | Что означает в контексте | Чем проверять |
|---|---|---|
| Доступность | Пользователь может выполнить критический сценарий | SLI/SLO по операциям, error budget |
| Производительность | Скорость реакции системы на нагрузку | p95/p99 задержки, throughput |
| Масштабируемость | Как меняются ресурсы при росте нагрузки | Нагрузочные тесты, горизонтальный предел |
| Надёжность | Правильность результата при заданных условиях | Инварианты, тесты отказов, сверки |
| Отказоустойчивость | Способность продолжать ограниченную работу при сбоях | Fault injection, dependency isolation |
| Восстанавливаемость | Скорость/потеря данных при восстановлении | RTO/RPO, проверенные restore-тесты |
| Безопасность | Контроль доступа и защищённость активов | Threat model, authz-тесты, аудит |
| Развёртываемость | Возможность выпускать изменения с допустимым риском | Deployment frequency, rollback rehearsal |
| Тестируемость | Возможность доказать корректность отдельных частей | Изоляция компонентов, скорость и качество тестов |
| Изменяемость | Стоимость корректировки бизнес-функции | Change lead time, blast radius |
| Наблюдаемость | Возможность понять состояние системы | Метрики, логи, трассировки, алерты |

Нельзя механически выставить всем свойствам «максимальный приоритет». Выберите небольшой набор **архитектурно значимых** свойств; остальные всё равно требуют разумного минимума.

## Сценарии качества: шесть полей

1. **Источник:** кто вызывает событие или воздействие.
2. **Стимул:** что произошло (пик трафика, сбой, атака, релиз).
3. **Среда:** обычная работа, деградация, миграция или авария.
4. **Артефакт:** какая часть системы рассматривается.
5. **Реакция:** ожидаемое поведение.
6. **Критерий измерения:** наблюдаемый результат с величиной и временем.

### Пример: восстановление подписки

- Источник: платёжный провайдер.
- Стимул: одно событие оплаты доставляется повторно.
- Среда: сервис недавно перезапущен.
- Артефакт: Billing и Subscriptions.
- Реакция: подтверждение обрабатывается идемпотентно; активная подписка не продлевается дважды.
- Критерий: в тестовом наборе из N повторов существует ровно одно логическое применение события и запись об аудите. **N согласуется при спецификации теста.**

### Пример: производительность (показатели лишь иллюстративны)

~~~text
Критический API: GET /subscriptions/current
Среда: 300 одновременных пользователей
Критерий: p95 < 250 ms, ошибки < 0.5% в течение 30 минут
Исключения: явно описанные деградации внешних зависимостей
~~~

Не переносите это число в реальный проект без замеров и бизнес-согласования.

## Приоритизация и конфликт

Таблица для встречи с заинтересованными сторонами:

| Свойство | Если не обеспечить | Что мешает | Как проверить |
|---|---|---|---|
| Корректность оплаты | Финансовые ошибки | Асинхронность, дубликаты | Инварианты + тест повторов |
| Скорость вывода функций | Потеря времени выхода | Сложная доставка | Lead time + rollback |
| Работа при сбое внешнего шлюза | Нельзя оформить заказ | Внешняя зависимость | Chaos / fault tests |

Удобно ранжировать как **обязательно**, **важно**, **можно ухудшить**; лучше добиваться согласия на уровне сценариев, а не абстрактных слов.

## Область действия свойства

Не всё обязано выполняться на уровне всего приложения. Например, поиск по каталогу может быть eventual consistent, а применение платежа — строго идемпотентным и согласованным. Отсюда идея **архитектурных квантов** (глава 7): степень независимой развёртываемости и связанности частей влияет на область обеспечения свойств.

**Ошибка:** требовать одинаковые SLA от уведомлений, платежей и аналитики только потому, что они относятся к одному продукту.

## Функции пригодности: свойства под контролем

«Система модульная» не является проверкой. «Архитектурный тест запрещает импорты между внутренними пакетами Billing и Accounts» — проверка.

| Желаемое свойство | Проверяемый механизм |
|---|---|
| Контроль циклических зависимостей | Static dependency analysis в CI |
| Сохранность платежных событий | Тест атомарной записи и повторной обработки |
| Восстанавливаемость данных | Регулярный тест восстановления из резервной копии |
| API-совместимость | Consumer-driven contract tests |
| Развёртываемость | Canary/rollback процедура и измеряемое время |

Функция пригодности должна иметь владельца, частоту выполнения, порог, реакцию на нарушение и место в CI/операционном процессе.
