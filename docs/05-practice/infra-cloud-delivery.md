# Архитектура ↔ инфраструктура ↔ облако ↔ эксплуатация

**Книга:** облачные подразделы архитектурных стилей (главы 10–18) и пересечения из главы 26. Настоящий раздел расширяет материал инженерными проверками, не привязанными к поставщику облака.

## Структура приложения не равна инфраструктуре

Код может быть прекрасно разделён на модули и при этом развернут одной неустойчивой копией без резервного копирования. И наоборот, Kubernetes не исправит монолитную модель данных и циклы бизнес-зависимостей.

В каждом проекте проектируются **две связанные топологии**:
1. Логическая: кто отвечает за поведение и данные.
2. Физическая: где работает код, как развёртывается и какие отказные зоны существуют.

## Набор вопросов по инфраструктуре

| Область | Вопрос |
|---|---|
| Вычисления | Как увеличиваются capacity и число экземпляров? |
| Хранение | Где durable state, резервные копии и восстановление? |
| Сеть | Какие зависимости синхронные, какие имеют таймаут? |
| Secrets | Кто выдаёт, ротирует и отзывает ключи? |
| Identity | Как аутентифицируются сервисы и авторизуются операции? |
| Deployment | Можно ли выпустить новую версию без недопустимого простоя? |
| Monitoring | Как заметить нарушение пользовательского SLO? |
| Incident response | Кто дежурит, как откатить, где runbook? |
| Cost | Чем измеряется полезная нагрузка на единицу стоимости? |

## Выбирать физическую платформу после требований

- **Один сервер / VM:** низкая сложность, но ограничение по отказоустойчивости и масштабированию; приемлемо в некоторых контекстах.
- **Несколько VM / контейнеров:** гибкость изоляции и масштабирования с ростом требований к сети и управлению.
- **Managed services:** часть операционной работы переносится поставщику, но появляются зависимость, стоимость и ограничения API.
- **Serverless:** может быть удобен для нерегулярной событийной работы, однако cold start, лимиты и стоимость вызовов требуют замеров.
- **Оркестрация контейнеров:** оправданна при соответствующем масштабе и требованиях; не цель сама по себе.

## Critical path и распространение отказа

Предположим, клиент вызывает API, тот синхронно обращается к Billing, а Billing — к внешнему платёжному провайдеру. Время ответа и доступность критической операции зависят от всей цепочки. Для каждого перехода задайте timeout, retry budget, допустимую деградацию и предел параллелизма.

Таймаут на каждом участке без общего бюджета может сделать end-to-end ожидание неожиданно длинным. Повторы без лимита при перегрузке усиливают инцидент.

## Стратегии безопасного изменения

1. **Backward-compatible migration:** сначала схема поддерживает обе версии кода, затем обновляются пользователи схемы, затем удаляется старое.
2. **Rolling/canary:** небольшая доля запросов на новую версию с наблюдаемыми условиями отката.
3. **Feature flags:** отделить выпуск кода от активации функции, но не забывать удалять старые флаги.
4. **Rollback:** заранее проверять, можно ли вернуться к прежнему формату данных; обратный деплой не всегда обратим.
5. **Recovery drills:** резервная копия не считается достаточной без проверенного restore.

## Безопасность и данные

- Минимальные привилегии и явное authorization на каждую чувствительную операцию.
- Изоляция production/secrets и контроль доступа к журналам.
- Защищённые каналы и управление идентичностью сервиса.
- Проверка webhook authenticity и защита от replay там, где применимо.
- Ограничение персональных данных в events, логах и аналитике.
- Для нормативных требований — отдельная проверка юрисдикции и актуальных обязательств.

## Наблюдаемость

**Метрики** отвечают, сколько и насколько часто; **логи** — какое событие произошло; **трассировки** — где конкретный запрос задержался. Ни одна из трёх систем в одиночку не обеспечивает всей наблюдаемости.

Полезная иерархия: SLI критического сценария → зависимые сервисы → инфраструктура. Алерт «CPU 80%» без пользовательского эффекта часто слабее, чем нарушение error budget.

## Deployment / review checklist

- [ ] SLO согласованы и измеряются на стороне пользователя.
- [ ] Определены dependency timeout и общий бюджет.
- [ ] Существуют восстановленные из backup данные в тесте.
- [ ] Проводился сценарий отказа важнейшей зависимости.
- [ ] Есть регулярная ротация секретов и проверка доступа.
- [ ] У релиза есть критерии остановки и отката.
- [ ] За incidents и costs назначены владельцы.
