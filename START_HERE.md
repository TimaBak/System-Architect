# С чего начать: путь системного архитектора

Архитектура ПО — дисциплина принятия решений в условиях ограничений. Цель обучения — не выучить наизусть топологии, а уметь обосновать структуру конкретной системы, выявить её слабые места и согласовать изменения с людьми.

## Три траектории

| Для кого | Маршрут | Практическая проверка |
|---|---|---|
| Разработчик, переходящий в архитектуру | Основы → стили → коммуникации → ADR | Спроектировать приложение с явными границами |
| Технический лидер | Свойства качества → риски → команды → архитектурные ограничения | Провести архитектурное ревью существующего проекта |
| Solution/System Architect | Контекст → выбор стиля → интеграции → данные → инфраструктура → эксплуатация | Защитить решение перед бизнесом и инженерами |

**Рекомендуемый порядок:** сначала [мышление](docs/01-foundations/architecture-thinking.md), [модульность](docs/01-foundations/modularity.md), [свойства](docs/01-foundations/quality-attributes.md), [компоненты](docs/01-foundations/component-design.md); затем [сравнение стилей](docs/02-styles/README.md), [принятие решений](docs/04-decisions/architecture-selection.md) и практика.

## Модель работы с каждой темой

1. **Проблема.** Назовите симптом или требование без упоминания любимой технологии.
2. **Контекст.** Укажите команду, данные, ожидаемую нагрузку, SLO, бюджет, риски и сроки.
3. **Гипотеза.** Объясните, каким структурным решением предлагается обеспечить свойство.
4. **Альтернативы.** Сравните минимум два варианта; обозначьте, чем жертвуете.
5. **Граница.** Установите владельца компонента, данных и интерфейса.
6. **Проверка.** Превратите декларацию в тест, метрику, ограничения зависимостей или эксперимент.
7. **Решение.** Зафиксируйте мотивы в ADR с датой и условиями пересмотра.

## Практикум: от требований к архитектуре

**Задача.** Небольшая команда создаёт платформу подписок. В первой версии: регистрация, каталог тарифов, оформление подписки, оплата через внешнего провайдера, уведомления и кабинет. Нужно быстро выйти в релиз и сохранить возможность роста.

### Шаг 1. Не гадать про стек

Сначала запишите вопросы: сколько пользователей ожидается, есть ли пики, какие деньги теряются при простое, допустима ли задержка уведомления, должен ли личный кабинет работать при недоступном платёжном провайдере, где хранятся персональные данные, кто дежурит по инцидентам?

### Шаг 2. Выделить свойства

Например, **корректность состояний подписки**, **восстанавливаемость платежей**, **развёртываемость небольшими изменениями** и **наблюдаемость**. Численные целевые значения пока не придуманы: их нужно согласовать с заказчиком. Образец спецификации — [шаблон сценария качества](templates/quality-attribute-scenario.md).

### Шаг 3. Определить ответственность

Первые кандидаты в модули: Accounts, Plans, Subscriptions, Billing, Notifications, Support. Подключение к платежному шлюзу не должно автоматически делать его владельцем бизнес-истины о подписке. Определите источник истины отдельно.

### Шаг 4. Выбрать границы развёртывания

Гипотеза для небольшой команды — модульный монолит с независимой фоновой обработкой. **Это не универсальный рецепт.** При особых SLA, командах и нагрузке сервисная архитектура может быть лучше. Сравнение — в [матрице стилей](docs/02-styles/README.md).

### Шаг 5. Проверить ошибки

Как ведёт себя оформление подписки при повторной доставке webhook? Что происходит, если запись оплаты подтверждена, а уведомление не отправлено? Что будет при недоступности базы? Важна не схема «счастливого пути», а восстановление после частичного отказа.

### Шаг 6. Записать ADR и проверить экспериментом

Зафиксируйте альтернативы, измерения, операционные последствия и триггеры пересмотра. Подготовьте прототип одного критического сценария.

## Порядок самостоятельной тренировки

- **Уровень 1:** объяснить девять стилей собственными словами без названий технологий.
- **Уровень 2:** написать по два сценария качества с измеримыми условиями.
- **Уровень 3:** разложить систему на компоненты и обосновать границы данных.
- **Уровень 4:** оформить три решения ADR: стиль, транзакции, интеграция.
- **Уровень 5:** провести мини-ревью: риски, метрики, наблюдаемость, rollback, безопасность.
- **Уровень 6:** представить решение аудиториям бизнеса, разработки и эксплуатации разными словами.

## Самопроверка

Можете ли вы ответить: «Почему нельзя просто сделать микросервисы?», «Как мы узнаем, что архитектура ухудшилась?», «Кто владеет конкретным фактом о клиенте?», «Что мы теряем при асинхронном взаимодействии?», «Как отменить решение, если допущения изменились?».

Если нет — не заучивайте термин: вернитесь к контексту проблемы и конкурирующим свойствам.
