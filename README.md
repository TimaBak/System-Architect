# System Architect

> Открытый русскоязычный инженерный справочник по архитектуре программных систем: от требований и свойств качества до архитектурных решений, эксплуатации и развития продукта.

**Цель:** помогать понимать архитектуру, сравнивать альтернативы и проектировать системы с объяснимыми компромиссами. Это не каталог «правильных» технологий и не учебник по одному стеку.

## Основной принцип

**Не существует универсально лучшей архитектуры.** Есть набор требований, ограничений, допущений и стоимость каждого решения. Архитектор должен объяснять не только *что* выбрано, но и *почему*, *почему не альтернативы*, *какие риски остаются* и *когда выбор стоит пересмотреть*.

Полезная рабочая последовательность:

```text
Контекст бизнеса и пользователи
        ↓
Сценарии качества + ограничения + риски
        ↓
Границы домена и логические компоненты
        ↓
Варианты архитектуры и анализ компромиссов
        ↓
ADR + данные + взаимодействия + развёртывание
        ↓
Проверки свойств архитектуры и наблюдаемость
        ↓
Эксплуатационная обратная связь → пересмотр решений
```

## Правила использования

- **Сначала свойства, потом стек.** Kubernetes, Kafka или микросервисы сами по себе не являются бизнес-целью.
- **Фиксируйте границы.** Модули, владение данными, зависимости и ответственность команд важнее названий сервисов.
- **Делайте допущения видимыми.** Масштаб, SLO, нагрузка, состав команды и бюджет всегда конкретны.
- **Проектируйте отказы.** Для распределённой системы таймауты, повторные доставки и частичные сбои — норма.
- **Проверяйте решения.** Метрика без порога и владельца редко помогает управлять архитектурой.
- **Не путайте примеры с требованиями.** Все учебные проекты в этом репозитории — модели, а не описание чужой производственной инфраструктуры.
